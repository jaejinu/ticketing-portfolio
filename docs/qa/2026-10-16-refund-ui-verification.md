# 환불 진행 상태 연결 및 검증 (2026-10-16)

## 변경

- `PaymentResponse`, `PaymentDetailResponse`의 `refundPending`을 관리자 및 관객 화면에서 사용한다. 좌석 정보를 보강한 상세 응답에도 값이 보존된다.
- 관리자 결제 목록·내 티켓 목록·상세에 ‘환불 처리 중’을 표시한다. 처리 중에는 3초, 평소에는 10초마다 조회한다.
- 환불 중인 결제의 단건 환불 버튼을 숨기고 해당 회차의 일괄 환불을 비활성화한다. HTTP 요청 중에는 다른 환불 요청도 막는다. 확인창이 열린 뒤 비활성화되어도 확인 버튼이 이를 따른다.
- 요청 성공과 실패 모두 결제 목록을 재조회한다. PG 장애 응답도 서버에 환불 의도가 저장된 경우가 있기 때문이다. 자동 복구로 환불 완료되면 이전 단건 요청 오류 안내를 숨긴다.
- V015는 환불 요청 여부·관리자·사유 및 복구 대상 조회 인덱스를 저장한다.

## 자동 검증

- 결제 모듈: 51개 테스트 통과. 실패한 환불의 자동 복구, PG 취소 뒤 DB 저장 실패 복구 및 상세 응답의 환불 상태 보존을 포함한다.
- 가격 모듈: 이전 단계에서 26개 테스트 통과. 정상 수요 0과 집계 불가 구분, 구역별 대체 수요, 조회 중 오류의 부분 집계 폐기를 포함한다.
- 프론트 lint, production build, typecheck 통과.
- Chromium 데스크톱·모바일, WebKit 모바일: 전체 129개 브라우저 테스트 통과. API 모의 응답 기반이다.
- 완료 후 오류 안내 제거·일괄 환불 비활성화의 마지막 변경 후 환불 관련 12개 테스트를 세 브라우저 구성에서 재실행해 모두 통과했다.
- 추가한 화면 시나리오: PG 오류 이후 관리자 화면의 진행 상태·자동 완료·중복 요청 방지, 내 티켓 목록과 상세의 자동 완료.

## 실제 로컬 연동 검증

기존 데모와 분리한 임시 Timescale/PostgreSQL(15440), Redis(16390), Kafka(19092), Mock PG(18087)를 사용했다. local 프로필 백엔드(8088)와 production 프론트(3002)를 실행했다. Kafka 입력 토픽 `pricing.demand.v1`을 생성한 뒤 Streams RUNNING을 확인했다. Mock PG는 저장소의 서버·파일 저장 코드를 사용하고, 테스트용 미들웨어로 취소 경로에만 503을 주입했다. 실결제는 없다.

Playwright Chromium에서 실제 로그인 폼으로 관객과 관리자를 로그인했다. 테스트 준비의 회원가입·공연 선택·대기열 입장·좌석 확보는 실제 REST API로 수행하고, 결제와 관리자 환불은 브라우저 버튼으로 수행했다. 홈에서 좌석 선택까지 전부 클릭한 시나리오는 아니다.

1. 정상 결제 → 관리자 환불 → 관리자 ‘환불됨’ 표시 → 좌석 AVAILABLE 확인.
2. 두 번째 결제 후 PG 취소에 503 주입 → 관리자 ‘환불 처리 중’ 및 환불 버튼 제거 → 내 티켓 상세 ‘환불 처리 중’ 확인. 이 시점의 좌석은 SOLD 유지.
3. PG 장애 해제 → 추가 관리자 요청 없이 스케줄러가 환불 완료 → 관객 ‘환불 완료’, 관리자 ‘환불됨’, 좌석 AVAILABLE 확인.
4. 두 결제 모두 확보 후 시간 경과에도 저장된 점유 금액과 결제 금액이 일치했다(각 80,000원). 실행 중 기준가보다 높은 가격 틱 16건을 DB에서 확인했다. 브라우저 가격 차트의 모든 실시간 전파를 검증한 것은 아니다.
5. 최종 DB: REFUNDED 2건, PAYMENT_REFUNDED Outbox 2건, 환불 감사 기록 2건. 중복 완료 이벤트가 없었다.

임시 서비스와 테스트 컨테이너는 검증 후 종료했다. 실제 PG, 실제 iPhone Safari, 프로세스 재시작을 포함한 브라우저 장애 시나리오는 이번 검증 범위에 포함하지 않았다.
