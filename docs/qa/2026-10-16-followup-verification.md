## 이번 후속 수정

1. **환불 완료 실시간 전파:** `PaymentEventConsumer`가 `PAYMENT_REFUNDED`를 구독한다.
   구매자 개인 `/user/queue/payments` 채널로 전달하며 같은 이벤트를 중복 전파하지 않는다.
   관리자 환불 사유는 구매자 메시지에 포함하지 않는다.
2. **내 티켓 공통 갱신:** `useMyPayments`를 목록·상세에서 공유한다. 결제·환불 이벤트와
   재연결 때 즉시 재조회하며, 3초/10초 폴링으로 이벤트 유실을 보완한다.
3. **일괄 환불 결과:** 자동 복구로 완료된 결제를 최신 목록과 대조하여 완료·미완료 건수를 갱신한다.
4. **회차 전환:** 이전 회차의 확인창과 요청 결과를 초기화하고, 환불 HTTP 요청 중 회차 변경을 막는다.
5. **최신 상태 확인 실패:** 회차·결제 조회 오류를 표시하고 재조회 동작을 제공한다.
   오래된 결제 목록으로 환불을 요청하지 않도록 단건·일괄·열려 있는 확인 버튼도 비활성화한다.
6. **문서:** V015, 환불 복구, 실시간 전파, 현재 테스트 목록을 갱신하고 과거 QA 판정과 현재 결과를 분리했다.

## 실제 연동 검증

기존 데모와 분리한 임시 Timescale/PostgreSQL(15440), Redis(16390), Kafka(19092),
Mock PG(18087), 백엔드(8088), production 프론트(3002)를 사용했다.
Kafka 입력 토픽을 준비한 뒤 Streams RUNNING을 확인했다.
Mock PG는 저장소 구현을 사용하며, 테스트 미들웨어로 취소 경로에만 503을 주입했다.

- 테스트 계정 생성은 실제 REST API, 로그인은 실제 브라우저 폼을 사용했다.
- **공연 목록 → 공연 상세 → 대기열 → 좌석 선택 → 좌석 확보 → 결제 → 관리자 환불**을
  Chromium 브라우저로 두 차례 수행했다. 이전 단계의 API 기반 좌석 확보보다 검증 범위를 넓혔다.
- 첫 결제는 정상 환불, 두 번째는 PG 취소 장애를 주입했다.
- 장애 중 관리자와 내 티켓 상세의 ‘환불 처리 중’, 중복 환불 버튼 제거, 좌석 SOLD 유지를 확인했다.
- 장애 해제 뒤 추가 환불 요청 없이 자동 복구됐고, 관리자 ‘환불됨’, 관객 ‘환불 완료’, 좌석 AVAILABLE을 확인했다.
- 실제 브라우저 WebSocket 수신 프레임에서 두 번째 결제 ID의 PAYMENT_REFUNDED를 확인했다.
- 최종 DB는 REFUNDED 2건, PAYMENT_REFUNDED Outbox 2건, 환불 감사 기록 2건이다.
- 확보 후 시간이 지나도 점유 금액과 실제 결제 금액이 일치했다.
- 실제 Next 서버에 다른 Origin의 로그인 POST를 보내 application/json 및 text/plain 모두 403을 확인했다.

위 실연동은 임시 로컬 환경의 Mock PG 검증이다. 실제 결제사를 통한 금전 환불, 실제 iPhone Safari,
부하 한계 검증을 뜻하지 않는다. 테스트 앱과 세 컨테이너는 종료했으며 기존 데모는 변경하지 않았다.
