# Frontend — 다이나믹 프라이싱 티켓팅

> Next.js 16 (App Router) + React 19 + TypeScript 5 + Tailwind 4 + TanStack Query 5 + STOMP

Hybrid v1 디자인을 적용한 티켓 예매 프론트엔드입니다. 홈·공연 목록·상세·대기열·좌석 선택·결제·예매 완료·내 티켓이 REST API와 연결되어 있습니다.

## 디자인 시스템과 화면 구조

- 기준: [Figma Hybrid v1](https://www.figma.com/design/gGv1j4VDdu2EIBiwrAcH90?node-id=106-738)
- `app/globals.css`: 시맨틱 색상, 타이포그래피, 여백, 반경과 공통 레이아웃. 화이트/웜 그레이 바탕에 버건디 액션과 딥 그린 강조를 사용합니다.
- `app/layout.tsx`: IBM Plex Sans KR와 Instrument Serif, 전역 헤더·푸터, 본문 바로가기.
- `components/ui`: Button, Input, Card, Notice. 로딩·오류·빈 상태와 키보드 포커스를 공통 처리합니다.
- `components/booking`: 단계 표시, 공연 정보, 티켓 요약을 대기열·좌석·결제·내 티켓에서 재사용합니다.
- `components/show/ShowCatalog.tsx`: 홈과 목록의 검색·판매 상태 필터·공연 카드를 공유합니다.
- `components/auth/AuthLayout.tsx`: 로그인·회원가입의 공통 브랜드 영역과 폼 배치. 가입 후에도 예매 목적지를 유지하고 내부 경로만 허용합니다.
- 내 정보와 가격 알림도 공통 토큰을 사용하며 알림 목록은 UUID 대신 공연명·회차·구역을 표시합니다.
- `public/posters`: 7개 공연별 SVG 아트워크. 재즈의 반복 리듬, 클래식의 동심원과 건반, 록의 대각선, 팬미팅의 궤도 등 장르별 구성을 사용합니다.
- 페이지는 데이터 연결과 화면 조합을 담당하고 API 계약은 `lib/api`에 유지합니다.

데스크톱은 최대 1440px, 좌우 여백 64px입니다. 1023px 이하에서 예매 영역을 한 열로 전환하고, 767px 이하에서는 여백 20px와 44px 좌석 버튼을 사용합니다. 좌석 행은 줄바꿈 없이 지도 내부에서 스크롤합니다.

공연명·포스터·회차·가격은 실제 API 응답을 표시합니다. Figma의 예시 공연, QR, 가격·좌석 번호를 고정 데이터로 넣지 않습니다. `SeatDetails`가 결제 응답의 seatIds와 서버 좌석 배치를 연결해 구역·열·번호를 표시합니다. 회차별 좌석 메타데이터는 5분간 공유 캐시하며, 일부 번호를 찾지 못하면 수량과 재조회 안내를 표시합니다. 예매 상세는 `/me/tickets/[paymentId]`에서 본인 결제 내역을 기준으로 조회합니다.

## 예매 상태 처리

- 좌석/가격 STOMP 갱신과 REST 재조회(좌석 15초, 가격 10초)를 병행합니다. 판매된 좌석은 선택 합계에서 제외하고 가격을 확인할 수 없으면 확보 버튼을 비활성화합니다.
- 비로그인 대기열·좌석 진입은 로그인으로 연결하고 공연·회차·쿼리를 복귀 주소로 유지합니다. 대기열 진행 중 세션이 만료되어도 같은 기준으로 로그인에 연결합니다. 공연 목록·상세는 비로그인으로 볼 수 있습니다.
- 대기열은 서버 순번과 예상 시간을 표시합니다. 연결 실패·만료·요청 제한을 구분하며 임의 진행률은 표시하지 않습니다.
- 결제 금액과 만료 시간은 hold 응답이 기준입니다. 만료 시 새 결제를 막고, PENDING은 결과를 조회합니다.
- 응답 유실 시 같은 hold의 Idempotency-Key를 재사용합니다. 결제 완료 후 내 티켓 캐시를 갱신합니다.
- 로그인·로그아웃·인증 만료 때 계정별 Query 캐시와 STOMP 연결을 정리하여 이전 계정의 정보를 재사용하지 않습니다.
- 현재 백엔드는 Mock PG를 사용하므로 결제 화면에 체험 결제 안내를 제공합니다.

## 브라우저 검증

```bash
pnpm exec playwright install chromium webkit
pnpm build
pnpm test:e2e
```

Playwright가 3012 포트에서 빌드 결과를 실행합니다. 데스크톱(1440px)과 모바일(390px)에서 검색·필터, 상세→대기열→좌석→결제→내 티켓, 만료 차단, 결제 응답 유실 재시도, 가격 조회 실패, 대기열 재연결, 회원가입→로그인 목적지 유지, 외부 리다이렉트 차단, 좌석 번호·예매 상세, 가격 알림 등록·해제, 계정 전환 캐시 정리, 비로그인 공연 조회를 검증합니다. 입력 오류의 접근성 연결과 로그인 처리 중 중복 제출 차단도 포함합니다. 기본 실행은 Chromium 데스크톱·모바일과 WebKit 모바일의 총 93개 테스트를 대상으로 하며 전체 통과했습니다. 실시간 알림·지연 조회 경합과 WebSocket 재연결 복구도 포함합니다. 모바일 추가 점검에는 320px 좁은 화면과 667px 가로 화면도 포함됩니다. 스크린샷과 실패 trace는 `test-results/`에 생성됩니다.

테스트는 API 응답을 브라우저에서 모킹합니다. 아래 실제 연동 확인과 구분하여 반복 실행합니다. 실제 서버 WebSocket 검증은 아래 별도 기록을 참고하며, 대규모 부하는 별도 검증 대상입니다. 개발 서버의 3002 포트와 분리되어 있으며 사용자 데이터에 예매 요청을 보내지 않습니다.

### GitHub Actions 자동 점검

워크플로: [frontend.yml](../.github/workflows/frontend.yml). 프론트엔드 또는 이 워크플로가 바뀐 PR과 `main` push에서 실행되며 수동 실행도 지원합니다. GitHub에 반영된 뒤 동작합니다.

1. Ubuntu 24.04·Node 22에서 `packageManager`에 지정한 pnpm으로 frozen lockfile 설치.
2. 운영 의존성 High 이상 감사 → 린트 → 프로덕션 빌드 → 타입 검사. 빌드에서 Next 경로 타입을 먼저 생성하므로 새 체크아웃에서도 타입 검사를 실행할 수 있습니다.
3. Chromium·WebKit과 Linux 의존성을 설치하고 기존 3개 프로젝트의 브라우저 테스트 실행.
4. HTML 리포트·스크린샷·실패 trace를 `frontend-browser-report-<시도 번호>` 아티팩트로 7일 보관.

CI에서는 worker를 2개로 제한하고, `test.only`가 있으면 실패합니다. 실패 테스트를 한 번 더 실행하되 재시도에서만 성공한 flaky 테스트도 CI 실패로 처리합니다. 같은 브랜치에 새 변경이 들어오면 이전 실행을 취소합니다. 저장소 읽기 권한만 사용하며 백엔드 배포·운영 계정·추가 secret은 필요하지 않습니다.

로컬에서 같은 Playwright 설정으로 확인하려면:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm build
pnpm typecheck
CI=true pnpm test:e2e
pnpm exec playwright show-report
```

`playwright-report/`와 `test-results/`는 Git에 포함하지 않습니다. GitHub에서는 Actions 실행 화면의 아티팩트를 내려받아 HTML 리포트를 열거나, 실패 trace를 `pnpm exec playwright show-trace <trace.zip>`으로 확인합니다. 이 자동 점검은 모의 API 회귀 검사이며 실제 Safari 조작과 서버 부하 검증은 별도입니다.

참고: [Playwright CI](https://playwright.dev/docs/ci), [Playwright 설정](https://playwright.dev/docs/test-configuration).

2026-10-05 검증: 워크플로는 actionlint를 통과했고, 로컬 Node 22에서 frozen 설치·린트·빌드·타입 검사와 `CI=true` 전체 93개 테스트가 재시도 없이 통과했습니다. 재연결 테스트는 해제된 구독을 누적 집계하던 오류를 수정해 STOMP 구독 ID별 활성 상태를 확인하며, 세 브라우저에서 각각 5회 반복한 15개도 통과했습니다. GitHub Ubuntu 최초 실행에서 모바일 WebKit 좌석 선택의 스크롤 경합이 발견되었습니다. 기능 테스트는 `reducedMotion: reduce`로 스크롤 애니메이션을 줄이고, 장애 주입 전에 선택 완료를 확인합니다. 최종 실행 결과는 저장소 Actions에서 확인할 수 있습니다.

변경 시 코드 토큰, Figma 의미 변수, 메인 컴포넌트, 화면 인스턴스를 함께 검토합니다. 자동 동기화나 Code Connect 게시 설정은 포함하지 않습니다. 신규 화면은 공통 컨트롤을 재사용하고, 추가 상태가 필요하면 페이지별 CSS를 늘리기 전에 컴포넌트 계약을 갱신합니다.

## 모바일 예매 UX

좌석 선택과 결제의 `BookingAction`은 768px 미만에서 화면 하단에 고정됩니다. 좌석 선택은 **예상 총액**, 결제는 서버 hold 응답의 **확정 금액과 남은 시간**을 표시합니다. 콘텐츠·하단 메뉴가 가려지지 않도록 하단 공간과 포커스 스크롤 여백을 확보합니다.

좌석 스냅샷·실시간 갱신에서 선택한 좌석이 사용 불가로 바뀌면 해당 좌석만 제외하고 나머지 선택은 유지합니다. 충돌·연결 문제에는 사용자용 안내와 새로고침, 대기열 만료에는 재입장을 제공합니다. 좌석 확보 요청은 자동 재시도하지 않습니다.

결제 전 1분 이내에는 화면과 스크린리더로 안내하고 매초 타이머는 자동 읽지 않습니다. 확보 시간이 끝나면 주 동작이 좌석 재선택으로 바뀝니다. 이미 결제 요청을 보냈다면 시간 만료보다 결과 확인을 우선하며, 응답 유실 시 기존 멱등키를 재사용합니다. 새로고침으로 복원한 SOLD hold의 PENDING 결제도 최종 결과까지 조회합니다.

추가 브라우저 시나리오: 충돌 후 남은 좌석 유지, 모바일 실행 버튼의 화면 하단 위치, 1분 안내→만료→재선택, 결제 진행 중 만료, SOLD hold의 결제 결과 복원. 실제 결제·알림 발송 없이 모의 API로 검증합니다.

사용성 점검에서 대기열 입장 만료와 가격 조회 실패의 복구 동작을 `BookingAction`으로 통합했습니다. 입장 만료 시 하단 버튼은 **대기열 다시 입장**, 가격 조회 실패 시에는 **가격 다시 확인**으로 바뀝니다. 가격을 다시 불러와도 선택한 좌석은 유지됩니다. 좁은 화면·가로 화면에서 페이지 넘침, 좌석 터치 영역, 가로 스크롤과 Space 키 선택도 검증합니다.

### 실제 WebSocket 재연결 확인 (2026-10-05)

실행 중인 앱(3002)과 로컬 백엔드(8088)를 연결한 Chromium에서 확인했습니다. WebSocket 프레임은 모의 응답으로 바꾸지 않고 실제 서버로 전달했으며, 검증 중 브라우저 연결 하나만 의도적으로 끊었습니다.

| 확인 항목 | 결과 |
| --- | --- |
| 실제 좌석 hold 생성·해제 → STOMP 수신 | HELD·RELEASED 수신 및 좌석 활성 상태 변경 확인 |
| 연결 중단 후 자동 재접속 | seats·pricing 구독 재개 확인 |
| 연결 중단 중 다른 계정이 좌석 확보 | 수정 전에는 재연결 직후 조회 횟수 1→1, 좌석 선택 가능 상태 잔존. 수정 후 1→2로 즉시 조회하고 선택 불가 반영 |
| 로그아웃 | 연결 종료 확인 |
| 다른 계정 로그인 → 다른 회차 진입 | 새 연결에 새 회차의 seats·pricing만 구독, 이전 회차 구독 없음 |

재연결 콜백은 재구독 직후 좌석·최근 가격·선택 구역 가격 이력을 다시 조회합니다. 인증 세션 종료는 기존 클라이언트 참조와 구독을 먼저 비우고 종료를 기다리며, 이전 연결의 지연 콜백이 새 연결을 지우거나 재활성화하지 못하도록 합니다. 컴포넌트 해제는 개별 `unsubscribe()`를 사용합니다.

수정 전후 실행에서 테스트 계정 4개가 생성되었고 임시 hold 4개는 모두 해제했습니다. 결제 요청은 보내지 않았습니다. 실제 확인은 로컬 Chromium 범위이며, 모바일 재연결은 모의 WebSocket 기반 회귀 테스트로 별도 확인합니다. `pnpm test:e2e -g 'reconnected subscriptions'`는 재연결 후 누락 좌석과 가격 이력 재조회, 선택 해제, 활성 구독 수를 확인합니다.

### 실시간 알림과 지연 조회 응답의 경합

좌석 조회를 시작한 뒤 수신한 STOMP 알림은 해당 조회 응답보다 우선 반영합니다. 초기 로딩 중 받은 알림도 보관하여 첫 배치에 적용하고, 다른 회차의 알림은 무시합니다. 공연·회차가 바뀌면 좌석 컴포넌트를 새로 만들어 선택과 실시간 상태를 분리합니다. 다음에 시작되는 REST 조회는 다시 서버 스냅샷을 기준으로 삼아 일시적인 이벤트 상태가 영구 고정되지 않도록 합니다.

`pnpm test:e2e -g 'live seat event'`은 모의 WebSocket에서 STOMP CONNECT/SUBSCRIBE/MESSAGE를 처리합니다. 초기·재조회 응답을 지연시키는 동안 좌석 확보 알림을 보내고, 뒤늦은 AVAILABLE 응답에 점유 상태가 덮이지 않는지 확인합니다. 남은 선택 유지, 다른 회차 알림 무시, 해제 후 이전 선택이 자동 복원되지 않는 것도 검증합니다. 이는 브라우저 메시지 처리 테스트이며 실제 Kafka→WS 브리지 전달·재연결이나 서버 이벤트 순서 보장을 검증한 것은 아닙니다.

### 좌석·가격 갱신 복구 자동 점검

최초 좌석 로드 실패와 이미 표시된 좌석의 재조회 실패를 구분합니다. 재조회 실패 시 마지막 배치와 선택을 유지하면서 오래된 상태임을 안내하고, 좌석 선택 변경·확보 대신 하단에서 최신 좌석 상태를 다시 확인하도록 합니다. 복구 응답에서 판매된 좌석만 선택에서 제외하고 나머지는 유지합니다.

가격 조회가 성공했더라도 선택한 구역의 가격이 누락되면 확보를 막고 **가격 다시 확인**을 제공합니다. 복구 후에도 선택을 유지하며, 이후 가격 폴링에서 예상 합계와 하단 요약이 새 가격으로 갱신되는지 검증합니다. 자동 점검은 모의 API 기반이며 실시간 STOMP 메시지 전달 자체를 검증한 것은 아닙니다.

### 대기열 제한·결제 조회 복구 자동 점검

대기열 티켓 발급 후 첫 상태 조회에서 429가 반환되면, 상태 확인 중 문구 대신 `Retry-After` 기준의 재개 카운트다운을 표시합니다. 제한 시간이 끝나기 전에 추가 조회하지 않고 이후 대기 순번 조회가 복구되는 것을 검증합니다.

결제 요청이 접수된 뒤 결과 조회가 실패하거나, 새로고침으로 복원한 SOLD 예매의 결제 내역 조회가 실패하면 **결제 결과 다시 조회** 버튼을 제공합니다. 이 동작은 GET 조회만 재실행하며, 결제 POST를 추가로 보내지 않습니다. 실패 확정으로 오해하지 않도록 안내하고 좌석 재선택도 유도하지 않습니다. 두 경우 모두 조회 복구 후 승인 화면으로 이동하며 요청 횟수가 증가하지 않는 것을 세 브라우저 프로젝트에서 확인했습니다. 이 오류 주입 검증은 모의 API 기반입니다.

### 실제 연동에서 발견한 인증 진입 오류 수정

비로그인으로 공연 상세에서 예매를 시작하면 대기열에 `AUTHENTICATION_REQUIRED`와 재시도 버튼이 노출되는 문제를 실제 로컬 API 연결에서 재현했습니다. 대기열·좌석 경로를 보호 경로에 포함하고, 최초 진입과 세션 만료 복구가 같은 경로 판별 함수를 사용하도록 수정했습니다. 실제 요청에서 로그인으로 307 이동하고 공연·회차 주소가 유지되는 것을 확인했습니다. 모의 API 테스트는 로그인 후 좌석 화면 복귀, 쿼리 유지, 만료된 인증의 재로그인을 세 브라우저 프로젝트에서 검증합니다.

수정 우선순위: 결제 중복·금액 오해·예매 불가 문제는 즉시 수정, 여러 참여자가 같은 단계에서 망설이면 동선·문구 개선, 단발성 취향 의견은 별도 기록합니다. 수정 후 동일 과제로 다시 확인하고 실제 관찰 결과 없이 성공률을 채우지 않습니다.

## 실제 로컬 연동 확인 (2026-10-05)

실행 중인 프론트엔드(3002)·백엔드(8088)·Mock PG를 사용해 테스트 전용 계정 두 개로 확인했습니다.

- 회원가입 → 로그인 → 대기열 입장 → 좌석 확보 → Mock PG 승인 → 내 티켓: 정상.
- 결제 전 새로고침으로 hold·확정 금액 복원, 승인 후 새로고침으로 예매 완료 복원: 정상.
- 결제한 좌석의 실제 메타데이터(S 구역 A열 1번)와 예매 상세 표시: 일치.
- 같은 좌석에 두 계정이 동시에 hold 요청: 성공 200 한 건, 충돌 409 한 건. 성공 hold는 테스트 후 해제.
- 별도 hold의 실제 5분 만료: 서버 EXPIRED 전환 및 결제 버튼 비활성화 확인.

로컬 DB에는 테스트 계정과 승인된 체험 예매 한 건이 남습니다. 실제 금액 청구는 없습니다. 이메일·앱 알림 발송은 실행하지 않았으며 가격 알림 테스트는 모의 API로 검증합니다.


## 같은 Wi-Fi에서 휴대폰 테스트

백엔드와 Mock PG를 먼저 실행한 뒤 프론트엔드에서 실행합니다.

```bash
cd frontend
pnpm dev:lan
# 여러 네트워크가 연결되어 있다면 Wi-Fi 주소를 직접 지정
LAN_HOST=192.168.1.100 pnpm dev:lan
```

터미널에 표시된 `http://<Mac의 Wi-Fi IP>:3004`를 같은 Wi-Fi의 휴대폰 Safari에서 엽니다. 위 IP는 예시이며 실제 주소는 네트워크 환경에 따라 달라집니다. Mac을 켜 두고 테스트 전용 계정을 생성해 사용합니다. 종료는 실행한 터미널에서 Ctrl+C입니다. 접속이 안 되면 같은 Wi-Fi인지, macOS 방화벽의 Node 연결 허용 여부와 공유기의 기기 간 통신 제한을 확인합니다.

- `scripts/lan-dev.mjs`는 선택한 사설 IPv4에만 바인딩합니다. 외부 호스팅이나 공용 배포가 아닌 신뢰할 수 있는 Wi-Fi용 개발 환경입니다.
- 브라우저 API와 WebSocket은 같은 주소의 `/__backend/api/v1`과 `/__backend/ws`로 연결합니다. 프록시는 로컬 `127.0.0.1:8088`만 대상으로 하며 허용한 Host·Origin을 검증한 뒤 기존 백엔드의 로컬 Origin으로 전달합니다. 백엔드 CORS 설정을 넓히지 않습니다.
- 인증 Route Handler는 로컬 백엔드로 직접 연결하며 refresh 쿠키는 HttpOnly를 유지합니다. 개발 HTTP 환경이므로 테스트용 계정만 사용합니다. 운영 환경의 Secure 쿠키 정책은 바꾸지 않습니다.
- 일반 개발·빌드와 별도인 `.next-lan` 캐시를 사용합니다. 외부 패키지 추가 없이 Node HTTP 프록시와 Next 개발 서버를 함께 실행합니다.
- LAN HTTP에서는 `crypto.randomUUID()`가 제공되지 않을 수 있어 `crypto.getRandomValues()`로 UUID v4를 생성합니다. 재시도에도 같은 결제 키를 쓰는지 세 브라우저 프로젝트에서 검증합니다.

구현 참고: [Next custom server](https://nextjs.org/docs/app/guides/custom-server), [개발 Origin 설정](https://nextjs.org/docs/app/api-reference/config/next-config-js/allowedDevOrigins), [Web Crypto getRandomValues](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues).

### LAN 연결 검증 기록 (2026-10-05)

Mac에서 실행한 Chromium·WebKit의 모바일 에뮬레이션으로 위 LAN 주소에 접속했습니다. API·인증·WebSocket은 실제 로컬 서버에 연결했습니다.

| 항목 | 결과 |
| --- | --- |
| 비로그인 예매 진입 → 로그인 → 원래 회차 복귀 | 두 브라우저 통과 |
| 대기열 입장 → 좌석 선택 → hold 생성 → 결제 화면 | 두 브라우저 통과 |
| 같은 주소를 통한 STOMP CONNECTED 수신 | 두 브라우저 통과 |
| refresh 쿠키 HttpOnly / 브라우저 페이지 오류 | 유지 / 오류 없음 |
| LAN HTTP Web Crypto | randomUUID 없음, getRandomValues 사용 가능 확인 |
| 예상하지 않은 Host·Origin 요청 | 각각 HTTP 403 확인 |
| 실제 iPhone Safari 키보드·회전·백그라운드 | 미실시 — 위 실기기 진행표 사용 |

구성·재검증 중 테스트 계정 3개가 생성되었으며 임시 hold 3건은 모두 해제했습니다. 결제 POST는 보내지 않았습니다. 모의 API 회귀 테스트는 UUID 대체 생성·동일 키 재시도를 포함해 93개 통과했고, 빌드·타입 검사·린트도 통과했습니다. LAN 서버의 첫 컴파일에서는 일반 빌드가 하위 캐시를 지우는 문제를 발견해 캐시를 `.next` 밖의 `.next-lan`으로 분리한 뒤 재검증했습니다.
